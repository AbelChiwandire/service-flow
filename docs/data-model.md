# ServiceFlow Data Model

## 1. Overview

ServiceFlow stores its data in **Neon PostgreSQL**, accessed through the `@neondatabase/serverless` driver. The schema lives in [`lib/sql/setup.sql`](../lib/sql/setup.sql) and is applied manually; there is no ORM or migration tool.

The MVP contains three entities:

- User
- Customer
- Job

A separate `Business` entity is intentionally excluded. Each account represents one business, so the business identity is stored as `businessName` on the `User` record.

> **Invoicing:** The original plan included minimal invoices for completed jobs. Due to time constraints, invoicing could not be added, and the data model, routes, and UI contain no invoice entity.

Column names use camelCase and are quoted in SQL (for example `"userId"`).

---

## 2. User (`users`)

The person who owns and manages a ServiceFlow account.

| Field          | Type         | Notes                                    |
| -------------- | ------------ | ---------------------------------------- |
| `id`           | UUID         | Primary key, generated by `pgcrypto`     |
| `name`         | VARCHAR(255) | Account owner's name                     |
| `businessName` | VARCHAR(255) | Business represented by the account      |
| `email`        | VARCHAR(255) | Login email, unique                      |
| `passwordHash` | TEXT         | bcrypt hash (10 salt rounds)             |
| `createdAt`    | TIMESTAMPTZ  | Defaults to now                          |
| `updatedAt`    | TIMESTAMPTZ  | Defaults to now, updated on every change |

`passwordHash` is never returned to the client; repositories select a public column set (`PublicUser`).

---

## 3. Customer (`customers`)

A customer receiving services from the business.

| Field       | Type         | Notes                                     |
| ----------- | ------------ | ----------------------------------------- |
| `id`        | UUID         | Primary key                               |
| `userId`    | UUID         | Owner; FK to `users`, `ON DELETE CASCADE` |
| `name`      | VARCHAR(255) | Customer name                             |
| `email`     | VARCHAR(255) | Customer email                            |
| `phone`     | VARCHAR(50)  | Customer phone number                     |
| `address`   | TEXT         | Service address                           |
| `createdAt` | TIMESTAMPTZ  | Defaults to now                           |
| `updatedAt` | TIMESTAMPTZ  | Defaults to now                           |
| `isDeleted` | BOOLEAN      | Soft-delete flag, default `false`         |
| `deletedAt` | TIMESTAMPTZ  | Set when soft-deleted                     |

Index: `idx_customers_userId`.

---

## 4. Job (`jobs`)

A service job performed for a customer.

| Field           | Type         | Notes                                     |
| --------------- | ------------ | ----------------------------------------- |
| `id`            | UUID         | Primary key                               |
| `userId`        | UUID         | Owner; FK to `users`, `ON DELETE CASCADE` |
| `customerId`    | UUID         | FK to `customers`, `ON DELETE RESTRICT`   |
| `title`         | VARCHAR(255) | Short job name                            |
| `description`   | TEXT         | Optional                                  |
| `scheduledDate` | DATE         | Required                                  |
| `status`        | `job_status` | Enum, defaults to `scheduled`             |
| `createdAt`     | TIMESTAMPTZ  | Defaults to now                           |
| `updatedAt`     | TIMESTAMPTZ  | Defaults to now                           |
| `isDeleted`     | BOOLEAN      | Soft-delete flag, default `false`         |
| `deletedAt`     | TIMESTAMPTZ  | Set when soft-deleted                     |

Indexes: `idx_jobs_userId`, `idx_jobs_customerId`.

### Status

`job_status` is a PostgreSQL enum:

```text
scheduled | in_progress | completed | cancelled
```

Allowed transitions (defined in [`lib/db/jobs/status.ts`](../lib/db/jobs/status.ts)):

```text
scheduled   → in_progress, cancelled
in_progress → completed, cancelled
completed   → (final)
cancelled   → (final)
```

## 5. Relationships

```text
User 1 ────< Customer 1 ────< Job
  └──────────────────────────< Job   (direct ownership)
```

| Relationship    | Cardinality |
| --------------- | ----------- |
| User → Customer | 1-to-many   |
| User → Job      | 1-to-many   |
| Customer → Job  | 1-to-many   |

There are no many-to-many relationships.

### Why `userId` is on both Customer and Job

Ownership could be inferred through `Job → Customer → User`, but a direct `userId` lets every query scope by owner (`WHERE "userId" = $session`) and keeps the ownership check a single comparison. The tradeoff is that ownership is duplicated, so `createJob` verifies that the customer belongs to the same user.

---

## 6. Business Rules

- Every query is scoped to the authenticated user's `userId`; one user can never read or modify another user's customers or jobs.
- **Soft delete:** deleting a customer or job sets `isDeleted = true` and `deletedAt`; rows are not removed. Soft-deleted rows are excluded from lists, counts, and lookups.
- A job must reference an existing, non-deleted customer owned by the same user.
- A customer with a `scheduled` or `in_progress` job cannot be deleted.
- A `scheduled` or `in_progress` job cannot be deleted; it must be cancelled first.
- Status changes made through the UI must follow the transition rules above.
- Deleting a user account cascades to that user's customers and jobs.

### Derived concepts

- **Upcoming:** active jobs scheduled today or later.
- **Overdue:** active jobs scheduled before today.
- **Lead:** a customer with no scheduled or in-progress jobs.
